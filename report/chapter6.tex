\section{Evaluation and Results}

This chapter evaluates whether the implemented observability stack can reconstruct incidents in the global control plane with enough evidence for practical diagnosis. The focus is scenario-driven: a healthy baseline, Atomix degradation, and API bid-flood congestion. Trigger and recovery automation is kept in \texttt{observability-testing-scripts/} so each run is repeatable.

\subsection{Evaluation Method and Workflow}

The testbed is the deployed Kubernetes environment from Chapter 5: API Gateway, Auction Runner, Telemetry Processor, Atomix, OpenTelemetry Collector, Prometheus, Alertmanager, Jaeger, and Loki. Signal flow is:
services $\rightarrow$ OpenTelemetry Collector $\rightarrow$ Prometheus/Jaeger/Loki, with alert delivery via Alertmanager $\rightarrow$ Telegram.

Each scenario run follows the same sequence:

\begin{enumerate}
    \item verify baseline health;
    \item apply one trigger;
    \item observe metrics, traces, logs, and alert state in the same incident window;
    \item restore the cluster before the next run.
\end{enumerate}

The scripts used are:

\begin{itemize}
    \item \texttt{./observability-testing-scripts/01-trigger-atomix-degradation.sh};
    \item \texttt{./observability-testing-scripts/02-trigger-bid-flood.sh};
    \item \texttt{./observability-testing-scripts/03-restore-cluster.sh}.
\end{itemize}

\subsubsection{Bid-to-Auction Trace Correlation}

To support cross-service diagnosis, this evaluation also validates trace correlation between API bid intake and Auction Runner bid processing. The API Gateway writes a propagated \texttt{traceparent} into bid state, and the Auction Runner later extracts it and links its \texttt{process-individual-bid} span to the originating API span. This bridges asynchronous execution through shared state (Atomix) without requiring direct RPC parent-child spans.

Operationally, this means an incident can be investigated from either side: starting at an auction-processing span and navigating to the originating bid-ingress trace, or starting at bid write and confirming downstream auction processing linkage.

\subsection{Evaluation Summary}

The evaluation shows that the observability stack can detect and explain two representative failure classes: dependency degradation (Atomix) and ingress congestion (bid floods). In both cases, incident interpretation is supported by synchronized evidence from metrics, traces, logs, and alert state.

The added bid-to-auction trace-correlation validation improves this result by linking API ingress events to later Auction Runner processing, which makes cross-service causality explicit in asynchronous execution paths.

Overall, the baseline and fault-injection runs support the project claim that coordinated observability evidence is practical for diagnosing control-plane incidents in the IXP system. The next chapter summarizes conclusions, limitations, and future directions.
